# Agent Note: Decisions 分阶段模板选择

Status: implemented

## 问题

用户需要根据原始图片中的数据选择适合重新排版的 widget 模板。一次发送原图和 30 模板总览的选择不能可靠区分数据结构：股票指数、热门话题和篮球赛程三个样例均选择 1 号，概率分别为 0.16、0.27、0.24。

## 决策

[测试脚本](../../../../design/test_openrouter_decisions.py) 使用两次 OpenRouter 请求，从 backend/.dev.vars 读取 OPENROUTER_API_KEY。第一阶段通过 Chat Completions 使用 openai/gpt-6.1-sol，第二阶段通过 Decisions 使用 openai/gpt-6-luna-decisions。[使用说明](../../../../design/README-decisions.md) 拥有运行方式与输出字段说明。

第一阶段仅发送原图，用严格 JSON Schema 限定 structure、item_count 两个枚举字符串，以及 summary 一句话中文摘要。摘要只描述可见内容，最多 120 字符，不给布局建议。数量选项为 1–20、超过 20、无法判断；一个带图表的指标、一条列表记录、一场双方对阵分别计为一条。max_tokens 为 512，包含推理 token，推理强度为 low。截断、拒答和非法字段会阻止第二阶段。程序按结构筛选 4–5 个模板，映射依据图表、指标、列表、成对实体、详情、日程、位置和人物媒体，不绑定股票或篮球等业务主题。

第二阶段发送原图、第一阶段包含摘要的完整判断和候选模板的单独裁切图，比较布局结构、阅读顺序、可读性和视觉比例。摘要补充业务内容和具体数据，候选映射仍只由 structure 决定。保留全部原始数据，允许重复卡片或延展列表行；模板示例中的无关头像、按钮等不要求保留。输出是模板样式选择，生成实际重排图片或 HTML 属于后续渲染工作。

第一阶段使用 Chat Completions messages/content 中的 image_url 图片。第二阶段按 OpenRouter 的 [Decisions 多模态格式](https://openrouter.ai/docs/guides/community/multimodal-decisions)，将图片直接放在 state 顶层数组，使用 image_url 对象及 base64 data URL；文字项为普通字符串。两个接口的图片组织方式不能互换。

模板图是固定六行五列目录。macOS sips 裁切候选图到临时目录，请求结束清理，不覆盖源图片。不新增 Python 第三方依赖。替换总览图必须保留模板身份及排列，否则编号与描述失配。

## 曾考虑的替代方案

**原图与完整总览一次选择。** 仅移除总览图、保留其它文字的对照分别选择 24、4、5，说明总览会影响该样例集合的判断。完整总览也要求一次完成内容识别、编号定位和视觉比较；分阶段提供可观察的中间判断，并缩小最后的图像比较范围。

**只用模板文字描述。** 原图加文字描述的对照能区分三类数据，但不能比较模板的真实视觉比例。最终选择仍使用候选裁切图片。

**为每个业务主题硬编码模板。** 股票和体育只是验证样例，映射应适用于相同数据结构的其它主题，因此使用结构分类。

**直接切换 OpenAI 接口。** 现有凭据属于 OpenRouter，其多模态接口已经过真实读图验证，不需要更换提供方。

**第一阶段继续使用 Decisions。** 两阶段 Decisions 的三个样例能区分结构，但用户指定第一阶段改用 GPT-6.1 Sol。该阶段需要两个短枚举结果和内容摘要，使用结构化输出；不要求聊天模型生成或模拟分类概率。

## 后果

概率只覆盖最终候选，不能与之前 30 选 1 的概率直接比较，也不是审美正确率。第一阶段分类错误会排除更适合的模板，因此输出保留分类结果和候选编号；source_analysis 包含分类、数量、摘要三个字符串，不包含概率或置信度。重复卡片或延展行只是排版策略，选择结果不证明实际布局已经保留所有数据。

两阶段有两次网络调用，分别按模型计费。Chat Completions 的 prompt_tokens/completion_tokens 在脚本中归一化为 input_tokens/output_tokens，方便合计。输出包含两阶段各自的请求 ID、用量和耗时，以及合计费用与总耗时；发生错误不自动重试。此探索脚本依赖 macOS sips；跨平台运行需要另行选择图片处理依赖。模板目录或分类集合改变时，要同步裁切网格、候选描述和结构映射。

## 验证

不含摘要的分类基准使用三个桌面样例，均通过真实两阶段请求：

| 样例 | 结构 / 数量 | 候选 | 选择 / 候选内概率 | 两阶段费用（美元） | 总耗时 |
|---|---|---|---|---|---|
| 1.png，股票指数与走势 | metric_series / 3 | 23、24、14、20 | 23 / 0.98 | 0.0020683 | 4.81 秒 |
| 2.png，热门话题排名 | ranked_list / 10 | 4、21、1、20 | 4 / 0.98 | 0.0034482 | 5.47 秒 |
| 3.png，篮球赛程和比分 | paired_entities / 7 | 8、12、4、16 | 8 / 0.60 | 0.0043146 | 5.47 秒 |

人工核对中，23 号提供单指标和走势图，可重复为三个指数；4 号提供列表行，可延展为十条话题；8 号提供双栏结构，可用于双方对阵并重复为多场比赛。篮球样例包含右侧部分可见记录，7 条与提示中的计数口径一致。三个结果符合结构选择目标；未生成重排产物，因此不作最终视觉质量保证。

第一阶段三次调用的输出用量分别为 19、20、19 tokens，均低于 512 上限。本地检查覆盖严格 schema、单图消息格式、输出上限、非法 JSON、非法枚举、多余字段、拒答和截断；第一阶段异常只发生一次请求。模拟完整流程核实两阶段端点、模型分离和用量合计。候选映射、裁切边界及输入、密钥、HTTP 错误处理沿用已有本地验证。语法检查和命令行帮助通过。相关记录与文档门禁为 npm run verify-notes、npm run verify-docs 和 git diff --check。

含 summary 的股票指数样例通过真实两阶段请求：摘要正确描述三项股指、点位、涨幅和走势图，第一阶段输出 71 tokens；最终选择 23 号，候选内概率 0.96，两阶段费用 0.0026837 美元，总耗时 5.68 秒。本地检查确认摘要完整进入第二阶段 state，并拒绝缺失、空白、超过 120 字符、多行和非字符串的摘要。
