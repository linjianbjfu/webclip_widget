# Agent Note: 列表识别图标与低对比度主题背景

Status: implemented

## 问题

Yahoo Sports session c6254e3b-638c-422a-bb47-04f2a50e2b98 的选区有 17 场比赛、34 个队徽及对应的深浅色版本，共 68 个 img。extra.js 只在 games.length === 0 时提取两张图，widget.html 也只在 hero 行创建 img。data.json 的首场两张图片分别约 7,915 与 7,991 字符，其余队徽字段为 null，不能据此判断原站读取失败。

图片政策对每次提取统一限制三张，适合少量主视觉，却阻止小队徽、头像、应用图标在重复条目中持续承担识别作用。现有背景规则允许淡背景，但缺少默认构图时主动评估主题装饰的要求，列表容易只有第一行有图、其余纯文字。

## 决策

### 根据内容选择图标与背景

背景素材规则由[背景装饰调整](../bug-fix/2026-10-12-widget-background-decoration.md)部分取代；本记录继续拥有跨条目用图和图片读取预算。

CORE、list/image 组件与 review 规定：来源图片能帮助识别重复条目时，优先让显示的条目使用对应小图，而不是默认只给首项用图。规则适用于任何题材，球队只是验证样例。图标与所属记录对齐，背景装饰不挤掉原本能显示的完整记录。前景图像尺寸、辅助文字及可选记录的容量取舍由[图片格式协商与视觉层级](../bug-fix/2026-10-09-image-format-and-visual-priority.md)拥有；本记录继续拥有跨条目用图与批次预算。

主体图片、条目识别图与背景分别评估。保留白色画布与有意义的浅灰分区，局部淡背景使用适合构图的来源图片，根据原尺寸截图调整；没有合适素材时省略背景，不自绘几何水印。正文始终不透明，背景不能伪装成真实业务图表或包含冻结的比分。

混合联赛列表不把某队徽铺成整张卡片背景，以免暗示所有比赛属于该队。可在重点比赛局部使用对应队徽水印，没有合适来源图片时保持白底。用户要求不用图时不加图片或主题图标；没有合适视觉素材时文字布局仍成立。

### 让小图标受字节与时间预算约束

每次提取支持最多 24 个图片候选，同时保留每 URI 180,000 字符、结果合计 360,000 字符的限制，不增加传输体积上限。大图与小图共用预算，优先分配给实际内容识别，背景复用已经取得的图片内容。相同来源可复用读取结果，但 data.json 中重复写入的 URI 仍计入总预算。

图片 helper 提供有界批处理，最多 3 个请求并行，整批取图时间预算 6 秒；单请求仍最多 3 秒、响应体 2 MiB。按候选顺序分配结果字符预算，避免网络返回先后决定哪些条目有图。到期停止新请求并取消未完成请求，失败项为 null，保证文字继续返回并为已有整体 15 秒提取时限留出空间。排队、异步解码与降级路径同样受时间预算约束；同步栅格化限制目标尺寸，并在返回前检查时限。

继续 fetch 原始字节并转 PNG/JPEG/WebP base64，保留透明通道，不用远程展示 URL，不修改源 img。现有 img 队徽已足以解决此 case；不引入图片搜索、截图背景、原网页 CSS 背景扫描或任意 SVG/字体资源搬运。有识别作用的前景主题图标可使用代码原生 CSS/SVG，但不能编造品牌或球队标识来冒充来源图，也不能用作自绘背景水印。

### 归属与旧产物

[产物协议](../../../../docs/protocol.md#widget-文件与截图)拥有图片预算与提取接口，[设计文档](../../../../docs/design-system.md)拥有用图与背景指导。规则作用于后续生成和修改，已有 bundle 不自动迁移。Yahoo 的原下载目录保留，新生成产物存于独立目录。

本决策补充[按内容用图](../bug-fix/2026-10-08-contextual-image-priority.md)、[白底层次](2026-10-09-white-layered-widget-style.md)和[空间利用](../bug-fix/2026-10-08-widget-space-utilization.md)，部分取代[图片字节提取](../bug-fix/2026-10-08-fetch-image-bytes.md)的三张串行预算。四篇记录继续拥有内容选择、正文容量及原图读取的理由，保留活跃并互相链接；无归档或删除。

[按信息关系分组与横向空间分配](../bug-fix/2026-10-09-widget-semantic-layout.md)补充组内关联、内容驱动的列宽和长名称回放；本记录的既有决策继续有效。

[按布局容量控制图标密度](../../implemented/bug-fix/2026-10-09-layout-driven-icon-density.md)规定当前显示数量与逐条用图的取舍，图片提取资源预算保持本记录的约束。

## 曾考虑的替代方案

**只加强“多用图”的 prompt。** 三张图片上限仍无法支持七行共十四个队徽，必须同步提取能力。

**仅提高图片数量、继续逐张等待。** 24 次三秒请求可能越过脚本总时限，文本提取也会失败，需要批次时限与有限并发。

**所有 widget 强制背景图或给每行增加大图。** 会破坏密集内容的可读性和容量；根据内容角色使用小识别图与局部背景。

## 验证

以下 CSS/SVG 背景证据记录收紧规则前的验证，不证明几何装饰美观；当前来源背景的正反例与真实生成证据由[背景装饰调整](../bug-fix/2026-10-12-widget-background-decoration.md)拥有。

- 图片浏览器测试覆盖 24 张透明图标、候选超限、三路并发、重复来源读取复用、乱序完成时按输入顺序分配总字符预算、批次取消、排队失败及异步解码超时。超时后完成的 bitmap 会释放；透明像素保持透明。原有 CORS、MIME/文件头、单图字符与响应体限制测试继续通过。
- 真实模型默认用图场景通过：七场比分使用十四张队徽，六个应用分别使用来源图标。相同生成 bundle 在换序、换图、名称更新、缺图和坏图时重放通过；检查图标与文字对应，失败不丢文字。新增负例拒绝只给首行配图、错误图片、错配记录、缺少明确要求的背景以及违反不用图偏好。
- 比分后续生成采用透明度 .08 的 CSS SVG 主题背景，保留七场比分与十四张队徽；保存产物及图片变体通过。后续不用图要求在独立真实模型会话中传入该 bundle 验证，七场文字保留，图片与主题图形移除。原尺寸截图已检查。证据在本机 downloads/design-check-eZCMLu、downloads/design-check-sUJYl0 与 downloads/icon-review/no-image。
- 混合模型命令未计为整轮通过：一轮被开发服务器热更新中断；另一轮的背景检测遗漏合法的伪元素背景。检测器加入伪元素支持，浏览器正反例证明淡背景可接受、缺少或不透明装饰被拒绝；保存的原 bundle 全部重放通过。无图后续请求单独完成。广告图省略和十条纯文本列表及变体也通过。
- Yahoo 原始 capture 重新生成的独立产物位于 downloads/icon-review/yahoo/f89f7fc1-e144-4a8d-95f5-a7532d24a0ed。原站执行识别 17 场比赛，24 个图片候选中一次读取取得 22 张、2 张失败；最终实际尺寸显示 8 场、16 张队徽及 .065 透明度主题线条。实时源内容可能变化。部分队徽的黑底存在于取得的原图字节中，不是提取器填黑；替代版本未证明始终透明，不对原图抠背景或编造标识。
- typecheck、设计目录门禁、brief/catalog 五项、SDK 六项、图片与样式/容量浏览器测试通过。图标检查最终重放另覆盖记录与图片关联，确定性检查拒绝错配记录。文档及笔记门禁通过。
- 稳定 brief 从 16,639 增至 17,281 UTF-8 字节；含案例的大号模式上下文从 10,372–12,240 增至 12,991–15,067 字节，均低于 18,000 字节门禁。按字节除以二估计，brief 增加约 321 token，各模式增加约 1,310–1,517 token；不是模型实际分词值。测量在 downloads/icon-review/prompt-{before,after}.json。

## 后果

小识别图能覆盖多个条目，背景可增加层次而不占正文行。候选增加会增加请求数，即使输出字节上限不变；整批超时或字符预算耗尽会让较后条目缺图。原站 CORS、防盗链、像素内容及解码失败仍限制可用素材，不能保证所有可见图片均可读取或适合白底。

helper 增加了上下文成本；有限并发、按顺序分配和整批时限共同防止请求扩张拖垮文字提取。透明度和美感仍需目视判断，不以机械分数替代。未部署生产环境，未验证 iOS 真机。
