# Agent Note: Widget Design System 与简洁图文生成风格

Status: implemented

## 问题

仅有可读、适应尺寸与静态截图要求，不能给模型提供具体的视觉组织方式。用户希望生成的 widget 更简洁，并可使用图形、线条甚至图片提升表现力；仅要求“不固定主题”不足以稳定引导这一效果。

随着布局、图形与用图规则增加，把全部内容持续写入 brief 会使规则难以维护，并让每轮生成加载不相关的细节。需要把可复用的设计知识与模型接入分开，让新增布局或调整设计值有明确的修改位置。

## 决策

### Design System 的职责与结构

Design System 面向生成模型，负责设计规则、默认设计值、组合方式和评审标准。模型根据用户意图、实际字段及可用素材选择构图，生成独立 HTML/CSS/SVG；不要求产物运行时加载组件库。

[分享讨论](https://chatgpt.com/s/t_6ac4c449ef148191b527f29010330932)建议分层组织设计知识，并由统一工具渐进加载。这里采用这一方向，接入已有 pi 会话和 preview_widget；不增加独立评审模型或结构化布局协议。

| 层次 | 拥有的内容 | 扩展方式 |
| --- | --- | --- |
| 核心原则 | 信息层级、简洁、真实数据、用户偏好、自动判断用图 | 少量稳定规则进入 brief；具体布局细节不进入核心原则 |
| 设计值（tokens） | 语义颜色、字体层级、间距、细线、圆角及三档尺寸下的建议值 | 用 surface、text.primary、accent 等语义名称；明暗变体修改映射，避免逐个布局改颜色 |
| 组件规范 | 主指标、信息行、状态标记、分隔线、进度、趋势图、图片区域 | 每项描述用途、数据要求、视觉关系和缺值处理；维护语义规范，不引入 React 或运行时依赖 |
| 布局模式（patterns） | 内容适用条件、组件组合、空间分配、尺寸适配及不适用情形 | 每种模式是一条独立定义；模型可调整组合，不强迫所有内容套进固定模板 |
| 案例与评审 | 参考图的构图分析、真实生成截图、应避免的问题 | 规则示例与实际生成验收分别维护；用可观察问题评审，不以随意的审美分数作为硬门禁 |

模式覆盖主指标、指标加趋势、状态或进度、同类条目列表和图文组合。图文组合承载模型主动复用网页图片的要求。日程、复杂分区等模式等真实案例需要时再添加；遇到目录未覆盖的内容，允许遵循核心原则自由组合已有组件，不把模式目录变成产品能力白名单。

tokens 提供默认值与角色关系，不把 160×160 等参考画布写死成根元素尺寸，也不改变用户明确的风格。明确区分默认建议与强制契约：数据真实、静态展示、交付与资源约束不可因设计模式改变；推荐间距、强调色与构图可以按内容调整。

### 单一来源与维护方式

生产定义放在 `backend/src/design-system/`：`core.ts`、`tokens.ts`、`components/`、`patterns/`、`examples/` 和 `review.ts`，用类型化对象与短文本保存。`catalog.ts` 仅组装定义与稳定 ID，不再维护另一份说明正文。原始图片保留在 `design/widget-style/`，设计值及行为规则不同时手抄进 Markdown、brief 和工具描述。文档解释维护流程并链接权威定义。

这些定义通过静态模块随 Worker 打包，不在运行时访问开发机目录或让模型猜仓库文件路径。`backend/src/agent/design-context.ts` 负责工具适配，brief 负责注入核心原则及自动生成的模式摘要，设计内容不依赖模型供应商或客户端框架。

新增模式需提供唯一 ID、适用说明、组件引用、数据前提、尺寸建议及相关案例，然后注册到 catalog。模式索引、工具参数枚举和返回内容从同一 catalog 派生；已有加载器与 brief 无需逐项修改。新增主题先体现为语义 token 映射，不预先引入主题商店、配置接口或版本迁移系统。发布更新影响后续生成，已交付 HTML 仍自包含，不随服务端设计值更新而改变。

### 按需加载与生成流程

只读工具 `get_design_context` 的参数为 `pattern`、`size` 和可选的 `include_examples`：pattern 的有效 ID 来自 catalog，另提供自由组合入口；size 复用既有 small/middle/large。工具自动带上所选模式需要的组件规范、对应尺寸 tokens、图片使用规则和简短评审要点，避免模型分别请求多个相互依赖的组件。

示意调用为 `get_design_context({ pattern: "image-text", size: "middle" })`。返回中包含模式 ID、设计指引、依赖组件与设计值。普通返回限定为一个模式及其依赖；请求案例时最多增加两份相关构图分析，按固定关联与稳定次序选择。案例返回文字分析，原始参考图用于维护者视觉校准；不把四张拼图固定附到每轮请求。若文字指引不足以稳定复现风格，再评估按需返回图片的收益、打包及上下文成本。

模型在阅读网页内容后选择模式；首次生成或实质性改变布局时加载相关设计上下文。普通对话不触发；同轮已经得到相同定义时不重复请求。核心原则、模式摘要和工具 schema 保持稳定排序。相较全量内嵌，按需加载增加工具往返；首轮上下文较少不等于完整任务 token 或耗时更低。

模型据此确定主信息、次信息、图形和可用图片，直接生成三个既有产物，再通过 preview_widget 检查截图与运行约束。构图决定不新增客户端文件或用户必须填写的设计表单。评审规则随所选上下文提供，由同一代理结合已有截图调整；审美判断与 preview_widget 的技术合格结果分别陈述。

图片的选择属于 Design System；图片如何经 extra.js 进入 data.json 属于提取与客户端协议。模式定义引用统一的用图政策，不分别实现图片提取。下文规定共同的图片使用与提取范围。

### 参考图与默认视觉方向

以 [widgets](../../../../design/widget-style/widgets.webp)、[widgets2](../../../../design/widget-style/widgets2.webp)、[StepCounter](../../../../design/widget-style/StepCounter.webp) 和 [instagramAndThread](../../../../design/widget-style/instagramAndThread.webp) 为设计参考，提取以下共性：

- 一个清晰的视觉焦点：主要数值、状态或标题优先，标签与辅助信息使用较弱的字号和颜色。通过留白、对齐和字重区分层次。
- 默认采用白色或柔和中性色底色、清晰的深色文字和少量强调色。内容适合深色或图片背景时可以采用，但必须维持文字对比度；用户指定的配色优先。
- 以整个 widget 为完整画面，保持一致的内边距和间距。减少重复标题、厚边框、重阴影及层层套卡片；不为留白挤掉用户显式点名或要求完整展示的内容，普通框选允许按主题取舍。
- 图形有明确作用：细线划分信息组，线性图标提示类别，小面积色块标记状态，环形进度或柱线图解释数据。有真实数据或相关图片时，优先用图形或图像表达主信息；必要文字仍可读，没有合适素材或用户要求不用图时采用文字布局。
- small 聚焦核心信息；middle 适合左右分区、并列指标或短列表；large 可安排主信息与明细。按内容和画布选择构图，不固定套用同一模板。

参考图里的交互按钮、装饰性页面外框和阴影不直接照搬。产物仍是完整、无需交互的静态截图；仅表达信息的状态标记可以保留。

### 图形和图片的来源

优先使用内联 CSS/SVG 制作静态线条、图标、几何插图和数据图形。图表的点、柱高、比例与进度必须来自实际提取的数据；没有历史序列时不画虚构走势，没有目标或分母时不画虚构完成率。装饰图形不得看起来像真实业务图表。

模型在设计 widget 时主动评估所选网页区域中的图片：与内容相关、符合 widget-style 参考图的简洁风格，并能在目标尺寸下帮助识别内容或改善构图时，选择提取并直接使用。用户无需明确提出“使用图片”，也不需要先决定用不用图；没有合适图片时采用文字、线条或图形布局，用户明确的用图偏好优先。判断应结合捕获画面和 DOM 中的图片信息，不能只因为存在 img 元素就选用。

位图也可来自已提供且可读取、可内嵌的合适静态素材，例如主题插图。不把参考拼图裁成业务素材，不把捕获截图作为带有旧数值的背景。涉及人物、商品或业务状态的图片必须与实际内容对应；不让模型编造 base64，不在 widget 运行时请求远程图片。

### 网页 canvas 内容不在支持范围内

若生成 widget 所需的核心内容只存在于原网页 canvas 的绘制结果中，没有可直接提取的 DOM 字段，则允许生成失败，明确说明无法提取所需内容。不要求读取网页 canvas 像素、解析绘图指令、进行 OCR、截取画布作为业务图片，或增加宿主截图接口来保证这类网页成功。捕获截图仍可帮助理解视觉含义，但不能替代可更新的数据来源。

页面包含 canvas 不等于整个页面不可用。所选内容可由普通 DOM 字段和 img 图片完整提供时，正常生成并忽略无关 canvas；同一信息在 DOM 中有可提取表示时，也可直接使用该表示。缺少核心内容时不以空白 widget、编造数值或捕获时的截图冒充生成成功。

这里排除的是原网页以 canvas 承载的内容。把已加载的普通 img 转成 base64 时使用临时画布，仍属于下文的图片编码机制，不意味着支持提取网页 canvas 内容。

### 选区图片通过 extra.js 进入 data.json

模型决定复用原网页图片后，生成对应的 extra.js 提取逻辑，在源网页上下文中取得图片内容，随其他字段返回 base64 图片数据。客户端将结果序列化到 data.json，widget 从该字段显示图片。图片 URL 不作为展示资源传递，避免 widget 再次请求时因防盗链、来源页或登录环境差异而加载失败。业务链接仍可独立存在，不用于加载图片。

图片字段使用带 MIME 的完整 data URI，例如 `imageData: "data:image/png;base64,..."`，不可用时为 null；字段名由同一 bundle 的提取与渲染脚本约定。图片与相应记录一起更新，不把首次捕获的图片固定进 widget.html。只选与所选内容相关、在 widget 尺寸下有价值的少量图片，不扫描整页或提取广告素材。

图片提取支持已有合法 PNG/JPEG/WebP base64 data URI，以及选中 img 的 HTTP(S) URL。URL 通过有界 CORS fetch 读取字节，预算内保留原图；超限图片可缩小，fetch 失败可尝试可读 img 的 canvas 转换。具体预算和客户端异步结果流程由[产物协议](../../../../docs/protocol.md#widget-文件与截图)拥有，取舍见[异步图片字节提取](../bug-fix/2026-10-08-fetch-image-bytes.md)。临时画布不修改页面，不读取原网页 canvas，也不扩大为页面截图或从图像识别业务数据。

widget 只接受约定的栅格图片 data URI；空值、格式错误或图片解码失败时隐藏图片或展示中性占位，保留原有文字和可读布局，不回退到远程 URL。宿主仍在数据渲染和图片加载结束后截图。

**浏览器读取限制。** 防盗链与像素读取权限是不同问题。已成功取得的 base64 可避免展示阶段的防盗链请求，但图片在源页面可见，不代表脚本能读出字节。普通模式加载的跨域图片绘入 canvas 后，toDataURL 会抛出 SecurityError；单独 CORS fetch 可能被允许，但仍受来源服务器和页面 CSP 限制。图片未加载、解码失败或画布不可读时，逐张返回 null，让文字提取继续；若用户要求这类图片也必须可用，需要 iOS 宿主提供图片字节获取或截图支持，单靠 extra.js 无法承诺实现。技术依据见 [MDN 的跨域图片与 Canvas 说明](https://developer.mozilla.org/en-US/docs/Web/HTML/How_to/CORS_enabled_image)。

**预览差异。** 服务端 preview_widget 使用 DOMParser 捕获文档且禁止网络加载，不能取得原网页已解码的远程图片像素。它可以验证已有 data URI 与缺图布局，但不能单独证明在线图片提取成功。CLI 原 URL 预览必须覆盖已加载图片转 base64，并验证图片经 data.json 在本地 widget 中显示；iOS WKWebView 行为另需真机验证。不为离线预览通过而硬编码截图图片或开启任意网络请求。

保持三文件交付和仅请求同目录 data.json 的资源约束。不加入图片搜索、图片生成服务或独立素材文件协议；不承诺复刻参考图中的写实 3D 素材。受限图片按逐图降级处理；本次不增加宿主接口。

### 模型上下文与改动位置

在 [brief.ts](../../../../backend/src/agent/brief.ts) 中接入 Design System 核心原则与模式索引，更新开头的设计目标和按需加载指引。通过 [session-factory.ts](../../../../backend/src/agent/session-factory.ts) 注册工具，复用现有 pi 调用、事件记录和恢复流程，不建立第二套模型请求循环。在预览指令中要求按已加载的设计规则检查视觉层次、对齐、留白、图文关系与实际尺寸可读性。

[架构文档](../../../../docs/architecture.md) 描述 brief、设计目录与工具的职责，[产物协议](../../../../docs/protocol.md#widget-文件与截图) 拥有设计、图片数据及资源边界。preview_widget 说明离线图片覆盖限制；CLI 允许已移除或隐藏的可选坏图降级，不放过仍可见的坏图。没有新增用户端风格选择器或固定模板引擎。brief 与工具 schema 的体积记录见下方验证证据。

### 笔记归属与实施范围

[内容密度决策](../bug-fix/2026-10-08-widget-content-density.md)拥有普通选区取舍、显式内容保护、图形与图像优先及可读字号的调整；本记录继续拥有渐进加载、设计目录与图片处理机制。

[按内容用图决策](../bug-fix/2026-10-08-contextual-image-priority.md)细化依据页面内容与展示目的选择图片的通用指引；图片读取能力和跨域限制继续由本记录约束。

本决策部分取代[静态 widget 决策](2026-09-30-static-ios-widget-artifacts.md)中“不规定配色、字体、圆角或装饰模板”的默认设计自由度，增加推荐层次与配色方向，但不固定色值、字体或模板。该笔记的尺寸、三文件交付、SDK 与截图约束仍独立有效，保留活跃并互相链接。[运行时 data.json](2026-10-01-widget-runtime-data-json.md)的数据来源和资源约束继续有效，没有需要归档或删除的笔记。

选区图片由模型根据内容和风格自主选择，经 base64 传递到 data.json。[直接执行脚本决策](../simplification/2026-10-01-direct-extraction-script.md)的自包含入口契约与[运行时 data.json](2026-10-01-widget-runtime-data-json.md)的传输流程可容纳图片字符串，仍保持活跃，并同步图片提取和离线预览的能力边界。

## 验证

代码包含 5 类布局及 freeform、7 项组件规范、4 份参考图分析、明暗 tokens 和统一图片政策。`get_design_context` 注册到真实 pi 会话，目录与参数来自同一 catalog。`verify-design-system` 已接入根 check；定义静态随 Worker 打包。图片提取代码作为可嵌入 extra.js 的示例返回，模型仍负责生成自包含脚本，客户端没有新增宿主函数。

已执行的检查：

- `npm test`：17 个文件、101 项通过，含目录负例、扩展发现与 brief 检查。
- `npm run test:agent`：5 项通过，含真实 SDK 调用设计工具及恢复工具结果。
- `npm run test:cli`：18 项通过；`npm run test:browser`：26 项通过。浏览器验证源图转 base64、同源/CORS/不可读图片、预算、坏图及 CLI 显示；可见坏图失败，已隐藏/移除的可选坏图保留文字布局。
- `npm run typecheck`、`npm run verify-design-system`、`npm run verify-docs`、`npm run verify-notes`、`git diff --check` 通过。目录门禁确认拒绝重复 ID、失效引用、非法尺寸和超预算上下文。
- `npm run deploy -- --dry-run --outdir /tmp/webclip-design-build` 成功；没有部署生产环境。

真实生成使用本地 Wrangler、配置的模型和 Browser Run，调用 [design-checks.mjs](../../../../test-cli/design-checks.mjs)。证据保留在本机 `downloads/design-check-FJqs1e/` 与 `downloads/design-check-fadWMd/`，包含三文件、data.json、截图和事件；下载目录不进入 git。已通过的案例为 small 核心指标（保留零值）、large 六条完整列表、middle 自主选图、同会话深色且不用图的修改、自由组合会议与阅读进度、缺历史时如实提示。截图已按实际尺寸目视检查；small/large 另通过宽高各增加 24 CSS px 的自适应检查。

生成的图文产物另经实际 CLI 在线预览：源图片接口要求来源页，直接请求返回 403；extra.js 在源页面将已加载图片转为 base64，widget 从 data.json 显示，未发出第二次原图请求。替换图片数据改变图片而保留文字，图片缺失时布局仍可读。生成的进度产物在 DOM 数值从 24 改到 76 后，进度条从 24% 变为 76%；零值显示 0%，缺目标时不绘制进度条。

canvas-only 案例完成了明确的不可提取说明且没有交付文件，未把截图里的数字写成固定业务值。含无关 canvas 的普通 DOM 指标仍成功生成。

首个完整趋势案例遇到 `Request timed out` 和 `recovery_exhausted`；独立测试服务上的第二次尝试还记录了 `Connection error`，最终以 `turn_timeout` 结束。第二批设计检查整体退出码为 1，不能描述为全量通过。

单独重跑 progress 案例使用原 endpoint、原凭据、同一模型和未修改的生成实现，最终通过，耗时 139,667 ms，设计工具调用 1 次、工具调用合计 10 次，累计 usage.totalTokens 为 78,258；没有观察到恢复。证据位于本机 `downloads/design-check-5BYqlp/`。七条历史数据正确呈现；另将历史第一项从 3200 改为 1000，柱高从 25.2898px 改为 7.90306px，截图和计算结果保存在该产物目录及 `downloads/design-diagnosis-20261006/`。这补齐历史序列正例与序列变化验收，不说明原超时问题已修复。

失败属于请求超时/连接错误与本地恢复机制的组合风险，不是已有证据支持的布局或趋势组件错误。旧失败记录没有调用 preview_widget，并反复读取源页面、加载设计上下文和写 extra.js。run-turn 仅在条目持久化时 markProgress，message_update 只广播；alarm 对超过 95 秒无持久化进度的运行执行恢复。恢复丢弃本轮部分消息上下文，且未取消仍在运行的旧执行。旧事件中较早开始的模型请求在较晚请求的结果之后完成，表明存在重叠执行；旧记录未保存每个流片段的到达时间，不能精确确认每次恢复时的网络状态。单次成功重跑也不能排除这一恢复缺陷。本次只诊断，没有修改恢复策略或放宽超时。

用户提供的新网关的 `/v1/models` 鉴权通过且列出相同模型，但 `/v1/chat/completions` 与 `/v1/responses` 的最小请求均返回 400，错误明确指向该模型无法通过上游 chat/completions 访问。因此未用它替换本地 dev vars，也未把网关不兼容当作原趋势失败的原因。

brief UTF-8 字节数从 9,746 增至 12,501，新增工具描述/schema 为 968 字节；按字节数除以 2 的保守估计分别为 4,873 → 6,251 和额外 484 tokens，非供应商实际分词。模式索引 427 字节；带案例的单次设计上下文为 5,515–6,480 字节，全量设计定义为 12,224 字节。本机 `downloads/design-prompt-measurement.json` 保存同口径记录。真实生成事件累计 usage.totalTokens 在已通过案例中为 8,253–276,876，耗时约 57–1,090 秒；恢复期间出现重复设计调用，不能据此宣称总成本下降。未完成无恢复干扰的全量内嵌对照，亦未验证 iOS 真机。

## 曾考虑的替代方案

**把全部设计规则追加到 brief。** 初期实现简单，但不同模式和组件的细节会挤占每轮上下文，规则与索引也容易分散维护。采用稳定核心加按需上下文，并实测工具往返是否值得；目录规模很小时全量注入仍是性能比较的基线。

**直接建立运行时组件库或完整布局 DSL。** 更容易限制 HTML 输出，但会增加渲染器、组件参数和兼容协议。当前产物是自包含 HTML，先采用语义组件规范；只有重复生成错误表明规范不足时，再评估固化具体组件实现。

**强制交付 layout-plan.json 并新增独立 Critic 调用。** 能让布局决定与评审独立观察，但增加文件协议、模型耗时、失败恢复和评分校准。先复用已有代理与截图工具，保留集中评审规则；真实案例若显示稳定的自评盲区，再决定是否加入独立模型评审，不先用未经校准的分数控制发布。

**每次生成都附上四张参考拼图。** 更直接地提供视觉样例，但增加图片上下文，并容易混入示例业务数据或照搬交互控件。先采用短文字指引与真实生成截图验收；若风格持续偏离，再评估按需提供视觉参考。

**固定一套 HTML/CSS 模板及颜色。** 容易统一外观，但新闻列表、单个数值与进度信息需要不同的空间分配。采用共同设计原则，由模型按内容构图。

**只传图片 URL。** widget 的新请求可能失去原页面的来源环境而触发防盗链，用户明确要求传递图片内容，因此采用 base64 data URI。

**只使用已加载 img 的 canvas 转换。** 无法读取普通模式加载的跨域图片，即使该服务允许 CORS fetch。[异步图片字节提取](../bug-fix/2026-10-08-fetch-image-bytes.md)拥有 fetch 优先与客户端等待结果的决策；设计系统继续拥有构图与内容选择。

**宿主获取受限图片，或另加图片生成服务。** 前者能扩大选区图片支持范围，但需要定义客户端接口、资源获取与刷新语义；后者不能替代真实业务图片。图片读取失败按逐图降级处理，不把宿主能力当成本仓库已具备的机制。

## 后果

模式和组件拆得过细会增加目录维护成本，按需加载也增加工具延迟；定义仅覆盖已有场景，成本判断需要完整任务的对照。tokens 与组件规范是生成依据，模型仍可能偏离，不能把存在目录或一次工具调用当作风格合格证据。独立评审模型及按需参考图片不在当前实现范围内，保留通过同一设计目录接入的空间。

提示词只能引导设计，无法保证每次生成的审美一致；真实样例是行为证据，不是对任意网页的保证。参考拼图的展示尺寸比实际 widget 大，字体、细线和图片需要以项目参考画布重新判断，不能照抄比例。

强调简洁可能使模型省略内容或过度缩小文字，因此可读性及用户要求的内容优先于装饰。图形和内嵌图片可能增大 HTML，素材使用应克制；默认风格也会增加 brief 长度，需要记录增量。已有 widget 必须重新生成或明确请求修改后才采用新指引。

base64 图片会增加 data.json 大小以及客户端序列化、解码和截图开销；不能把原网页所有大图照单全收。图片 fetch 受 CORS、CSP 及超时限制，Canvas 也不能读取所有可见图片。一次本地 Chromium 实验已验证：同源图片与 CORS 模式加载的授权图片可导出；无 CORS 跨域图片虽已显示，导出仍抛 SecurityError；DOMParser 中的图片 naturalWidth 为 0。这只是方案可行性证据，不代表产品流程或 WKWebView 已通过验收。

以网页 canvas 为唯一信息来源的图表、地图或自绘界面可能无法生成 widget，这是本次接受的支持边界。将来若扩展支持，需要单独定义可更新的数据来源与客户端能力；本实现不预建 canvas 提取或截图扩展接口。
