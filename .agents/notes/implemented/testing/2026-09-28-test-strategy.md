# Agent Note: 测试策略——三层划分与 e2e CLI

Status: implemented

## 问题

[工作区文件系统](../architecture/2026-09-28-server-workspace-filesystem.md)与[后端架构](../architecture/2026-09-28-backend-architecture.md)两篇列出了大量验收标准，但没有说这些标准**由哪一层测试承担**。不定这件事会有两种典型后果：要么全部挤进端到端测试，跑得慢、失败定位难、还要花 LLM 的钱；要么只写单元测试，而本系统最容易坏的地方恰恰都在组件的接缝上——DO 生命周期、SSE 续传、pi 的事件到流的桥接。

这个系统还有三件事使测试分层变得不可回避：

1. **一部分行为只在部署后才存在。** DO 的驱逐与保活是平台行为，本地 workerd 不复现——[实测](../architecture/2026-09-28-backend-architecture.md)那条 70 秒死线是在生产上量出来的，本地跑不出来。
2. **一部分行为花钱且不确定。** 真实 LLM 调用每次计费，且同一 prompt 不保证同一输出。断言不能建立在模型说了什么上。
3. **客户端是 iOS app，但服务端要先于它可用。** 没有一个协议级的客户端，服务端就没法在 app 写完之前被驱动和验证。

## 决策

三层，各自有明确的归属判据，加一个贯穿其中的 CLI。

三层都已建成：并置于 `backend/src/` 的用例跑在 Workers runtime 内（`npm test`），10 条端到端检查打真实服务与真实模型（`npm run e2e`），而 `test-cli/` 下的客户端同时是那些检查的夹具与 iOS app 就绪前驱动服务端的手段。

| 层 | 跑在哪 | 承担什么 | 花钱 | 期望时长 |
|---|---|---|---|---|
| 单元 | Workers runtime（Miniflare） | 纯逻辑与单组件：分块编解码、SSE 编帧、历史投影、turnId 校验、Outbox 合帧 | 否 | 秒级 |
| 集成 | Workers runtime，`runInDurableObject` 与 `runDurableObjectAlarm` | 接缝：DO 存储、alarm 的四条分支、协议语义 | 否 | 秒级 |
| e2e | 部署后的 Worker，真网络 | 平台行为与全链路：保活、驱逐恢复、真实 SSE 断线重连 | 可选真 LLM | 分钟级 |

### 单元与集成都跑在 Workers runtime 里

用 `@cloudflare/vitest-plugin`（当前 `1.1.13`，取代早先的 `@cloudflare/vitest-pool-workers`）。它把 Vitest 跑进 Miniflare，提供真实的绑定与**按测试文件隔离的存储**。

不在 Node 里用假的 `SqlStorage` 跑单元测试。理由是本设计对 SQLite 的依赖不是泛泛的"能存能取"，而是**具体的平台语义**：`exec()` 同步返回、2 MB 行上限、BLOB 往返不失真。一个自己写的假实现会把这些差异全部抹掉，于是通过的测试证明不了任何东西——而这些语义恰好是[文件系统篇](../architecture/2026-09-28-server-workspace-filesystem.md)整个选型的依据。

这套插件提供的几个辅助直接对应本系统的难点：

| API | 用来测 |
|---|---|
| `runInDurableObject` | 直接进入 DO 实例断言内部状态，不必经由 HTTP |
| `runDurableObjectAlarm` | **手动触发 alarm**——保活续排与中断检测的全部分支都靠它，不必等 30 秒 |
| `fetchMock` | 给 LLM 的出站 `fetch` 打桩，返回预置的 SSE 流 |
| `SELF.fetch` | 走完整的 Worker 路由，验证协议而非内部方法 |

**LLM 默认打桩。** 桩返回一段预置的 SSE，内容里带工具调用，使 agent 循环真实跑起来但输出确定。真实 API 只在一条单独的、默认跳过的通道里跑，用来验证 provider 兼容性（`thinkingFormat`、`maxTokensField` 这类），不参与常规断言。

### e2e 用一个 CLI 客户端

写一个 Node CLI，它是**协议级的客户端**，与 iOS app 使用同一套 HTTP + SSE 契约。

它有两个身份，两个都重要：

- **e2e 测试夹具**：能按脚本制造断线、重试、并发流，并把收到的事件序列导出为 JSON 供断言
- **开发期的驱动器**：在 iOS app 写完之前，用它驱动 agent 干活、看输出、调 prompt

第二个身份是它值得被认真写的原因——否则它只是个一次性脚本。edge-mac-widget 的 Node CLI 正是这个角色。

CLI 必须能做到的事，每一条都对应一个否则无法验证的失败模式：

| 能力 | 覆盖的失败模式 |
|---|---|
| 发 prompt 并消费 SSE，逐事件打印 | 流式是否真的从第一个 token 开始 |
| **在第 N 个事件后强制断开** | 断线是否丢事件 |
| 带 `Last-Event-ID` 重连并比对序列 | 续传是否有缺口或重复 |
| 重放同一个 `turnId` | 幂等是否生效、是否重复计费 |
| 同时开两条流 | 广播是否漏发、慢消费者是否拖垮 turn |
| 发完 prompt 立刻退出进程 | turn 是否在客户端消失后跑完 |
| 导出事件序列为 JSON | 让断言写在数据上而不是日志字符串上 |

### 本地测不到的，明确列出来

这几条只能在部署后验证，**不要试图在本地伪造**：

- **保活与驱逐**：平台行为，Miniflare 不复现。且单次验证要等 70 秒以上，不适合放进每次提交都跑的快路径——应当进 nightly 或手动触发的通道
- **真实 LLM 的 provider 兼容性**：只有打到真上游才暴露。**且它连集成层都上不去**——见下
- **iOS 侧的 SSE 与后台行为**：`URLSession` 的重连节奏、进后台时的连接命运，只有真机能说明

Browser Run 是个例外：`wrangler dev` 会在本地起 headless Chrome，因此 `preview_widget` 可以在集成层测。

**凡是导入 pi 包根的代码同样上不了集成层。** `@earendil-works/pi-coding-agent` 的入口会拉进它的扩展加载器，后者依赖 `node:process`；Workers 测试池按包的 `exports` 解析并保留该路径，而 wrangler 自身的打包器会静态剪掉它。实测结论是**同一份代码在 `wrangler dev` 与部署中正常，在测试池中启动即失败**。

这条推翻了本篇原先的一个假设——"集成层覆盖接缝"对 pi 接入不成立。受影响的是模型运行时、会话工厂与 turn 编排。**不要为了让它们进测试池而去 stub pi**：那样断言的不再是 pi 的真实行为，而集成层存在的理由正是验证接缝。

可行的缓解是把不依赖 pi 的部分——存储、SSE 编帧、广播、文件系统、shell——与 pi 接入切开，前者仍由集成层覆盖。

### 截图不做像素断言

`preview_widget` 返回截图、错误列表和 DOM 文本三样，**断言只写在后两样上**。字体渲染、抗锯齿、Chromium 版本都会让像素漂移，像素断言会变成一个周期性误报的来源，最终被人为忽略——那比没有断言更糟。

判断"widget 渲染对不对"用 `page.evaluate` 取 DOM 文本与关键节点是否存在；截图仅作为人看的证据留存。

## 曾考虑的替代方案

**只写 e2e，不分层。** 端到端最接近真实，看起来最省事。否决它的是三件事：每次跑都要等 DO 冷启与 LLM 往返，反馈周期从秒变成分钟；失败时只知道"整条链坏了"，不知道坏在哪一环；以及本系统大量的分支（幂等的三种状态、`GET /events` 的三种状态、慢消费者被踢）在端到端层面**极难稳定复现**，用 `runDurableObjectAlarm` 这类辅助在集成层触发才是可控的。

**在 Node 里用假 `SqlStorage` 跑单元测试。** 快，不需要 Miniflare。否决理由见上：本设计依赖的是 SQLite 的具体平台语义，假实现会把差异抹平，让测试失去证明力。

**对真实 LLM 做常规断言。** 最真实，但同一 prompt 不保证同一输出，断言只能写得极宽泛（"包含某个词"），那种断言抓不到回归。真实调用留给单独的兼容性通道。

**把 CLI 写成一次性测试脚本。** 省事，但会失去"iOS app 未就绪时驱动服务端"这个能力，而那正是开发期最需要的东西。把它当产品来写，成本只多一点。

## 验证

- 单元与集成套件在无网络、无 API key 的环境下全绿：71 条
- alarm 的四条分支由 `runDurableObjectAlarm` 在测试池内覆盖——保活续排、中断恢复、恢复次数耗尽、超过时限——无需等待真实的三十秒，也无需让对象真的失去宿主
- 端到端检查覆盖只有协议级客户端能触及的失败模式：在指定帧数处断开后重连，补发与原序列逐条对齐、无缺口无重复；重放已结束的 `turnId` 不向日志追加任何记录；一轮进行中的第二个 `turnId` 返回 `409` 并给出正在运行的那个；回放的 `turn_end` 只带元数据
- 断言全部关于协议行为，从不关于模型说了什么——同一提示不会两次产生同样的词
- 保活用例自证跨过了死线：实测 107.9 秒，客户端读一帧即消失，等待期间对该对象零入站请求
- 任何检查都不对截图做像素级断言

**pi 接入不在自动化覆盖内。** 导入 pi 包根会拉入需要 `node:process` 的扩展加载器，Workers 测试池保留该路径而 wrangler 的打包器剪除它。模型运行时、会话工厂与 turn 编排因此只能由端到端检查间接覆盖——它们跑通即说明这条链是通的，但没有针对性的用例。

## 风险

**集成层容易滑成"测实现而非测契约"。** `runInDurableObject` 能直接读写内部状态，用多了会写出一批锁死内部结构的测试，重构时成片失败却没有一个指向真实缺陷。**约束：涉及协议的断言一律走 `SELF.fetch`**，`runInDurableObject` 只用于制造前置状态与触发 alarm，不用于断言输出。

**打桩的 LLM 会掩盖真实的流式时序。** 桩可以瞬间返回整段 SSE，而真实上游是逐块到达且可能中途出错。据此写出的桥接代码可能在真实时序下才暴露缺陷（例如没有正确处理一个 chunk 跨越两次 `read`）。**桩必须能按指定的分块节奏逐块吐出**，而不是一次性返回。

**验证保活的用例在等待期间不能碰那个 Durable Object。** 会话列表由同一个对象提供服务，因此轮询它本身就是重置不活跃计时器的入站事件——检查会靠自己的请求撑过窗口，**即使保活被整个移除也照样通过**。等待必须是一段静默的 sleep，之后只查询一次。

**验证保活的用例必须自己证明它跑过了死线。** 一个客户端断开后完成的 turn 什么也说明不了：若它只跑了十几秒，本来就不会被驱逐。该用例要么让工具层产生超过 70 秒的真实耗时，要么在断言里比对 turn 的实际起止时刻——**只断言"跑完了"是一个会静默通过的假测试**。

**当前部署后通道是手工的，这正是它被跳过的前提条件。** 上面那些实跑是一次性手工执行的 curl，没有任何东西保证它们会再跑第二次。本篇原本就警告"需要时手动跑等价于不跑"，而现状恰是如此——**把它固定进可重复执行的脚本，是 CLI 之外本篇最紧的一项欠账**。

**部署后通道跑得慢且要花钱，容易被跳过。** 它覆盖的恰好是最难的那部分（保活、真实断线）。一旦因为慢而被长期跳过，那部分就回到了无人验证的状态。**应当固定进 nightly 而不是"需要时手动跑"**——后者等价于不跑。

**CLI 的双重身份可能让它偏向易用而非严格。** 作为开发驱动器会倾向于容错（自动重连、忽略异常事件），而作为测试夹具必须严格（任何缺口都要失败）。**两种模式需要显式区分**，默认严格；容错只在交互模式下开启。

**未定项。** 测试数据里的网页 source 从哪来（需要一组固定的、覆盖不同规模与结构的样本）；集成层是否需要一个最小的假 Browser Run 以避免每次都起 Chrome；以及 nightly 通道的失败如何通知。

## 后果

**换来了什么。** 反馈分成了两档：改动本地代码时 `npm test` 在五秒内给出答案，而协议与平台行为由一条可重复执行的命令覆盖，不再是一次性的手工 curl。CLI 顺带解决了另一个问题——服务端在 iOS app 存在之前就可以被驱动和观察。

**付出了什么。**

- 端到端检查每次运行都会真实调用模型，因此花钱、且耗时受模型速度影响；保活那一条独占三分钟，只在 `WEBCLIP_SLOW=1` 时运行
- 单元层因此不得不在 Workers runtime 内运行而非 Node 里，启动比纯 Node 慢——但这是有意的：本设计依赖的是 SQLite 的具体平台语义，假实现会把差异抹平
- turn 执行器为测试留了一个可替换的接缝。它是 pi 无法进入测试池的直接后果，不是设计上的洁癖

**两个本可静默通过的缺陷由这套检查自己暴露。** 一是保活的提示词依赖模型不合并调用，某次合并后 turn 只跑 52 秒、落在窗口内——守卫如实报失败而非给出假通过。二是原先每十秒轮询一次会话列表判断结束，而该列表由同一个对象提供服务，轮询本身就是重置计时器的入站事件；那个版本即使删掉保活也会通过。**第二个更危险：它不会失败，只会永远通过。**
