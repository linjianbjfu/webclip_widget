# Agent Note: 按布局容量控制图标密度

Status: implemented

## 问题

NBA session f9b6d54b-991b-40fd-90db-fb9fb888511d 在大号画布中显示两列三排比赛，共十二张队徽。widget.html 的队徽为 32×32px，球队行高却是 30px；相邻图像盒子已相互侵入，截图中上下队徽近乎贴合。渲染仅在比赛底边越过容器时删除最后一场，不能判断视觉拥挤。

CORE 与 REVIEW 鼓励可见记录都用对应图片，同时要求能放下完整行时继续增加记录。图片变大后，模型仍沿用几何上能塞下的记录数。提取成功、没有越界和文字可读，并不意味着图标数量适合当前构图。用户要求图标数量依据页面布局决定，不设固定个数。

session 71fd5470-8a48-497a-8a3e-4b889b5778cd 仍生成六场十二张图：30px 图片放进 30px 行，相邻队徽贴靠，渲染仅按底边裁切。按内容变化与不溢出的验证未覆盖默认构图质量；带有明确大图要求的成功对照，也不能证明普通请求符合默认用图目标。

## 决策

显示图标数量由页面含义、实际画布、图片可见主体大小、当前名称与数值，以及组内和组间留白共同决定。默认先为有表达价值的前景图片安排清晰的主体面积和周围留白，再决定列数与条数；密集的小图标网格即使不溢出，也须减少完整图文组并扩大图片。这个要求不依赖用户额外声明图片主导，简单图形与复杂队徽仍按实际视觉负担分别判断。图片读取预算约束资源消耗，不作为显示配额或文字记录上限；不设置通用图标数量、列数或面积比例。

CORE 区分显式记录要求和显式图片要求。相同角色的图文组保持一致，图片、名称、数值先组成可独立阅读的完整组；一个比赛按完整比赛分配空间。拥挤时先精简冗余文字和装饰，必要时减少可选完整记录。显式全部记录要求允许减少辅助图标，显式全部图片要求无法清晰容纳时说明冲突。重点图文组加文字次要组须有来源或用户指定的主次依据，不默认只给首项配图。

文字和图文列表都提取数量有界、足以评估布局的候选记录。渲染依据当前内容测量完整组，包括图片高度与组间留白；不能只看底边是否越界。用户未指定数量时，核心提示词禁止通过常量 slice 或循环次数预先限制展示数，即使其后还有布局测量。此要求由所有布局模式共用，不能只放在 list 模式中。

行容器须容纳图片、文字及周围留白，相邻图标不可贴靠；名称和数值列按当前内容分配宽度，验证长名称、状态增加与数字位数变化。图片保持可辨认，失败时仍有清晰文字身份。不增加精选或覆盖数量提示，不自动改写历史下载。图片读取、base64、透明度及批处理机制不变。

### 归属

[设计文档](../../../../docs/design-system.md)拥有当前使用规则；CORE、list/image 模式、row/image 组件、图片政策与 REVIEW 分别承担共用约束、局部布局、候选读取和截图复查。没有新增运行时布局引擎或全局视觉密度评分器。

本决策部分调整[条目图标与背景](../feature/2026-10-09-content-icons-and-backgrounds.md)的逐条用图取舍、[图片视觉层级](2026-10-09-image-format-and-visual-priority.md)的图片数量取舍，以及[空间利用](2026-10-08-widget-space-utilization.md)对“还能放一行”的判断。三篇继续拥有提取预算、格式协商和纯文字容量等独立理由，保持活跃并互相链接，不归档或删除。[信息分组](2026-10-09-widget-semantic-layout.md)继续拥有组内关联原则。

## 曾考虑的替代方案

**规定最多若干图标或固定两列两排。** 不能适应图片形状、名称长度、尺寸和内容差异，也违反用户不 hardcode 数量的要求。

**只增加行高，仍以不越界作为唯一容量判断。** 能修复本例的图像盒子相互侵入，无法保证一屏密集图标具有清楚的主次和分组，因此需要同时修改容量与用图判断。

**保留全部记录，统一缩小图标或默认只给第一项配图。** 前者削弱图片表达，后者无依据地制造主次。按内容关系与用户要求选择完整图文组或有意义的图文层级。

## 后果

清晰图片与分组留白会减少单屏记录数，显式全量时也可能少用辅助图标。没有来源主次依据时不任意制造重点。候选数据和渲染选择分离，使内容长度与画布变化仍可重新分配容量；字节与时间预算继续限制实际取得的图片。

技术检查通过不保证美观，也不能单靠长名称回放排除隐藏的固定展示上限，因此保留原尺寸截图检查和额外高度诊断。提示词不能保证任意页面一次生成成功。现有下载不自动迁移；未部署生产环境，未验证 iOS 真机。
