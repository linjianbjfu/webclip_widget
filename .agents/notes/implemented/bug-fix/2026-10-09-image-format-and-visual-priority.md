# Agent Note: 图片格式协商与以图为主的视觉层级

Status: implemented

## 问题

Yahoo session ba22ce34-2dd0-4f5a-8f8a-371db0b8a818 使用 20px 队徽、15px 队名和 18px 粗体比分，联赛与状态另占 76px。图片虽被提取，却只是文字旁的小点缀，不能充分表达队伍身份。用户要求决定用图后调整布局，尽量展示图片、弱化文字。

该产物的前两张队徽是 72×72 JPEG，像素完全不透明、角落为黑色。真实 Yahoo 来源下对同一 URL 的对照请求发现：默认 fetch 返回 JPEG，声明 Accept 为 image/webp,image/png,image/jpeg;q=0.8 后返回 WebP，分别有 3470 和 3166 个非完全不透明像素，角落 alpha 为 0。黑底来自 CDN 的响应格式协商，不能因为已取得字节就归为无法改善的原素材问题。证据在本机 downloads/image-emphasis-review/diagnostic.json；检测仅针对来源图片，未读取网页 canvas。先请求并缓存 JPEG 后，force-cache 加 Accept 仍返回旧 JPEG；改用 reload 加同一 Accept 后，两张均返回透明 WebP。对应证据在 diagnostic-cache.json 与 diagnostic-reload.json。

## 决策

### 声明支持的图片格式

图片政策和自包含 helper 保留 cors、omit credentials，采用 reload 缓存模式，并发送 `Accept: image/webp,image/png,image/jpeg;q=0.8`。只声明当前协议支持的静态栅格格式，不照搬浏览器包含 AVIF/SVG 的 Accept。继续校验真实响应的 MIME、文件头及大小，保留预算内返回字节与透明通道；不根据 URL 后缀认定格式，不回退远程显示 URL。

PNG/JPEG 仍是合法结果，照片无需透明；Accept 不能保证所有服务遵守格式偏好。对来源本来没有透明度的图片不自动抠图，不删黑色像素，不以 CSS 混合模式假装修复。现有批次、字符、并发与时间预算不变；同一提取器继续复用相同来源的读取结果。reload 避开可能忽略 Accept 差异的旧浏览器缓存，取回协商后的响应并允许更新缓存，不通过修改 URL 加随机参数绕过缓存。

### 图片承担识别，文字辅助解释

CORE、image/row、list/image-text、参考分析和 REVIEW 规定：选择有表达价值的图片后，先给主体图或识别图安排足够辨认的面积，再组织辅助文字。不要在既有文字布局里象征性插入小图标。优先压缩独占的元数据列、重复说明和装饰，把腾出的面积分配给图片；正文分组继续遵循当前布局规则。

当前赛事 case 使用 40px 队徽，球队图像与比分相邻，名称在下方辅助确认，联赛与状态放在比赛内的中央区域。布局按图像和字段关系决定，不固定两列模板。队名可以降低字重，弱化联赛/状态的色彩；在图片已承担主要身份识别、名称作为辅助确认时，可按本次明确的用户偏好使用较小但可读的标签。必要比分、排名、状态和点球限定信息不能丢失，不能让淡色文字失去对比度。

通用指引依据实际可见图案的面积而非 img 盒子尺寸判断图片是否足够大；包含大量透明内边距的素材需要更大显示空间，不能只检查 CSS 宽高。图片丰富程度、长宽比和画布共同决定布局，不设置所有图片统一最小尺寸或固定图文比例。背景图继续低对比度，不能因为强调前景图片而同步放大背景权重。

把有意义的图片视为内容参与容量分配，不再把“完全不影响原文字布局的条数”作为所有识别图的前提。先用布局和元数据精简保留更多完整记录；图片仍不可辨时，可以减少没有明确要求必须显示的记录，避免靠微小图标假装满足用图。显式条数/全量、关键字段和清晰阅读继续优先，纯文本列表不受图片层级规则影响。

### 文档与决策归属

设计文档与图片协议拥有当前规则。本决策部分调整[条目图标与背景](../../implemented/feature/2026-10-09-content-icons-and-backgrounds.md)对小图和记录容量的取舍，并补充[图片字节提取](../../implemented/bug-fix/2026-10-08-fetch-image-bytes.md)的请求格式协商；[按内容用图](../../implemented/bug-fix/2026-10-08-contextual-image-priority.md)和[信息分组](../../implemented/bug-fix/2026-10-09-widget-semantic-layout.md)继续拥有内容判断与字段关系。上述记录保留活跃并交叉链接，不归档或删除。

[按布局容量控制图标密度](../../implemented/bug-fix/2026-10-09-layout-driven-icon-density.md)拥有图片数量与完整信息组留白的取舍；本记录继续拥有格式协商与透明度策略。

## 曾考虑的替代方案

**只增加 Accept，保留 force-cache。** 已有 JPEG 缓存仍会被复用，真实浏览器对照未恢复透明；采用 reload，代价是每次提取需要网络请求。

**放大现有 JPEG 或仅切换源图片的深浅色版本。** 放大不能恢复透明度；同一 URL 的请求头已能决定 JPEG/WebP，先修复格式协商。深浅色版本仍按实际图案选择，不代替请求修复。

**删除黑色像素、使用混合模式或自动抠图。** 会破坏队徽本身的黑色图案，无法区分背景和主体，且本例有可取得的透明响应。

**只要求所有图标大于文字，或设统一大图尺寸。** CSS 尺寸不能代表实际图案面积，也不适合照片、封面、细节丰富图片与背景图的差异。采用角色与视觉层级判断，当前 case 的尺寸只用于对照验证。

## 后果

更大图片会占用空间，必须把记录容量与有效图像信息一起评估，不能一面要求图片主导、一面强制保持所有文字布局的密度。reload 增加网络读取，可能提高延迟和批次内的失败率，继续受现有时限约束，不因透明度协商增加第二次重试。较小的辅助名称可能降低熟悉程度较低的用户的识别能力，因此保留标签、清晰对比度和缺图布局。第三方 CDN 可能忽略 Accept 或错误缓存，透明响应需实测，已有 JPEG 产物不会自动恢复透明。

本次未部署生产环境，也未验证 iOS 真机。
