# Agent Note: 根据页面内容与展示目的优先用图

Status: implemented

## 问题

用户希望模型理解当前页面与 widget 的展示目的，自主判断图片的表达价值。游戏、商品和影视只是示例；用图选择依据图片是否有助于识别内容、传达信息或形成清晰构图，不能依赖几个题材名称触发。

用户提供的本地案例 `downloads/974f3d85-d4db-4423-8a56-4efc48d7b79d/` 来源于豆瓣电影。源选区含海报，生成的 extra.js 已调用 base64 图片提取器，widget.html 也包含海报布局，但 data.json 中三张图片均为 null。视觉选择与取得图片字节是两项不同的验证，增强用图指引不能替代图片读取能力。

## 决策

### 根据页面语义选择图片

[CORE](../../../../backend/src/design-system/core.ts)规定先理解用户目的、选区主信息，以及来源图片与内容的关系。图片能帮助读者识别主题、理解信息或扫读时，优先使用，不等待用户明确要求用图。图片可以是主视觉或辅助内容，具体地位由内容决定，并在实际尺寸下留出足够的可辨认空间。

判断适用于任何主题，不设置题材清单或固定模板。为图片让出空间时先减少重复标签与次要字段，保留必要文字、显式内容要求和来源优先级；无关广告、站点标志不能代替对应内容。没有合适图片或真实图表数据、实际尺寸下无法辨认、用户明确不用图时，采用可读的文字布局。

[模式](../../../../backend/src/design-system/patterns/index.ts)、image 组件与 review 补充构图和截图检查，不重复整套决策规则。主数值组件要求为字体字形留足行高，紧行框通过增加垂直空间处理，不靠缩字消除裁切。

### 图片内容与失败处理

[图片政策](../../../../backend/src/design-system/images.ts)要求 extra.js 取得所选来源图片的实际内容，编码为 PNG/JPEG/WebP base64 data URI，随对应记录写入 data.json。widget 使用图片字节，不直接加载原站图片 URL，避免展示阶段的请求触发防盗链、登录或来源检查；读取失败也不回退 URL。

已有合法栅格 data URI 可在预算内复用；已加载且像素可读的 img 使用现有转换机制。离线 preview 中的 null 不表示来源没有图片，生成代码保留适用的提取、图片显示与文字降级能力。最终回复区分候选图片、实际取得的图片和未验证或失败的读取，不能把无图技术预览通过描述为用图验证成功。

base64 解决取得图片后的传递与展示，不授予源页面读取跨域像素的权限。保留自包含 IIFE、图片预算、逐图降级与三文件协议，不增加下载代理、客户端取图接口、远程显示 URL 或捕获截图回退。无法取得内容时返回 null，并保留文字。

### 归属

本决策细化[内容密度决策](2026-10-08-widget-content-density.md)的通用用图判断，保留其内容取舍与字号规则；[设计系统决策](../feature/2026-10-06-minimal-widget-design-style.md)继续拥有渐进加载和图片提取边界。两篇旧记录保持活跃并互相链接，没有完全取代、归档或删除的笔记。[Design System 文档](../../../../docs/design-system.md)拥有使用与扩展说明。

## 曾考虑的替代方案

**以游戏、商品与影视封面为默认用图场景。** 具体示例容易引导模型，但也会把注意力限制在列举题材，忽略其他页面中图片的价值。采用基于页面语义与展示目的的通用判断，具体题材仅用于测试。

**允许 widget 直接加载图片 URL。** 展示时可能遇到防盗链、认证和跨域限制，不能替代原图内容传递。extra.js 的异步 fetch 属于独立的字节获取决策，见[异步图片字节提取](../bug-fix/2026-10-08-fetch-image-bytes.md)。

## 验证

- `npm test -- src/agent/brief.test.ts src/design-system/catalog.test.ts`：5 项通过；`npm run test:agent`：5 项通过；`npm run verify-design-system` 与 `npm run typecheck` 通过。
- `node --test backend/src/agent/images.browser.test.mjs`：2 项通过，覆盖实际图片转 base64、同源/CORS/不可读图片、防盗链、离线捕获、图片预算及坏图降级。已取得的 base64 在展示时不向原图接口发出第二次请求。
- [e2e:design](../../../../test-cli/design-checks.mjs)接入[图片场景](../../../../test-cli/design-image-cases.mjs)。本地 Wrangler、gpt-6.1-sol 与 Browser Run 的植物、电影、商品、无关装饰图及趋势图共 5 个场景、6 轮有成功产物。植物和电影未在用户请求中指定用图，图片实际进入 data.json 并显示；广告图被省略；商品场景的深色不用图后续修改得到遵守。原尺寸截图经过目视检查，图片可辨且必要文字可读。
- 植物和电影的来源记录与图片替换后，生成的提取器和 renderer 同步更新内容。无图、坏图与离线不可读远程图仍显示记录文字，无远程 URL 或捕获值回退。测试使用可重复生成的来源插图，不代表第三方网站读取已通过；电影插图替换后另重跑本地验证，确保海报内标题与记录一致。验收函数经负例确认会拒绝未提取有用图片、提取无关广告图和将捕获图片硬编码进 HTML。
- 成功产物、变体截图、事件及实际模型 usage 保存在本地 `downloads/design-check-fqGDR8` 与 `downloads/design-check-Ja6Uk1`。首个整轮命令因无关装饰图场景的文字行框裁切失败，不计整轮通过；补充字形行高指引后，`DESIGN_CASES=image-decoration npm run e2e:design` 退出 0，Browser Run 与本地复查通过。原失败结果保留。
- 豆瓣案例的离线重放仍返回三张 null；在线抽查的两张已加载海报导出时抛出 SecurityError，另一张未加载成功。证据在本地 `downloads/widget-image-review/`，不能据此声称豆瓣出图已解决。
- brief 从 14,431 增至 14,899 UTF-8 字节；按每四字符一个 token 粗估为 3,607 → 3,724，增量 117。六种模式、三档尺寸、含案例的设计上下文由 6,162–7,253 增至 6,949–8,060 字节，粗估 1,541–1,814 → 1,737–2,015 tokens。原文及测量在 `downloads/widget-image-review/context-{before,after,size}.json`；该估算不含工具 schema、源页面和截图，实际 usage 独立记录。
- `npm run verify-docs`、`npm run verify-notes` 与 `git diff --check` 通过。

## 后果

模型按内容判断用图，能覆盖未列举的主题，同时避免因页面存在图片就采用它。模型仍可能高估图片价值，牺牲必要信息，因此需要保留显式内容保护、节选提示与实际尺寸评审。真实生成仍可能出现布局失败，单次通过不能保证所有网页。

本次仅调整生成指引，不解除浏览器像素读取限制。[异步图片字节提取](../bug-fix/2026-10-08-fetch-image-bytes.md)拥有 fetch 优先的获取机制，本笔记继续拥有按页面含义用图的决策。现有 widget 不会自动变化；未部署生产，也未验证 iOS 真机。
