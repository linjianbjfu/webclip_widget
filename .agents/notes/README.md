# Agent Notes

这里存放一种设计文档。一篇 **Agent Note** 记录一个影响本代码库的决策或提案——*为什么这么做*、*放弃了什么*，也就是代码和文档本身承载不了的那部分。本文件规定 Agent Note 放在哪里、什么时候该写，以及[文件格式](#文件格式)。

## 目录结构与命名

每篇 Agent Note 有两个维度，都编码在它的**路径**里——`{lifecycle}/{class}/yyyy-mm-dd-topic-title.md`：

- **lifecycle**（顶层目录）是这篇 Agent Note 的状态，状态变化时文件在目录之间移动：
  - **`proposed/`** — 实施前先评审的提案，尚未落地（或只落地了一部分）。
  - **`implemented/`** — 决策已经上线。文件记录当时决定了什么、否决了什么，并且**与实际上线的东西保持同步**：后续代码移动了文件、重命名了包、改了某个键或默认值，就在同一个改动里更新这篇 Agent Note（只改事实——路径、名称、结构，不改决策本身）。见 [implemented/AGENTS.md](implemented/AGENTS.md)。
  - **`rejected/`** — 提案评估过并被否决。只在它的理由还能拦住一个有诱惑力、有实质代价的错误时保留；否则直接删除。
- **class**（嵌套目录）是决策的*种类*——见下面的[分类](#分类)。

文件名里的日期是这个议题**首次被提出**的日期（以 git 历史为准）。Agent Note 之间的交叉引用一律用相对 markdown 链接（`[议题](../../implemented/architecture/2026-…-….md)`），不要用裸的散文描述或编号——这样链接是可以机械校验的，并且在文件跨目录移动后仍然有效。

活跃的 lifecycle 树就是工作清单：浏览它的 lifecycle/class 目录，或者直接全库搜索。**不要新增集中式的 `INDEX.md`**——一份需要手工同步的索引只会和真实目录结构漂移。已实施、有历史价值但对未来工作指导意义不大的记录，移入下面描述的独立冻结树 [`archived/`](archived/AGENTS.md)。

## 分类

每篇 Agent Note 属于一个路径编码的 class，取自 `scripts/agent-note-tree.ts` 里的封闭集合；分类门禁会拒绝其它目录。新增一个 class 是一个需要慎重的动作：同时修改那份规范集合和本节。

| Class | 覆盖什么 |
|---|---|
| `feature` | 一个新的、面向用户或面向模型的能力。 |
| `bug-fix` | 修正一个缺陷，或者补上一个复盘暴露出来的缺口。 |
| `simplification` | 删掉代码、行为或者接口面，不新增能力。 |
| `architecture` | 关于**已发布源码**的结构性决策——包之间怎么关联、运行时词汇是什么。 |
| `process` | 代码**周边**的工具、策略或工作流——门禁、包管理器、vendoring——不是运行时行为。 |
| `testing` | 测试基础设施与测试策略。 |

`architecture` / `process` 的分界线：**architecture** 说的是我们发布出去的源码；**process** 说的是围绕它的工具和工作流。（`refactor` 是故意不设的——它和 `simplification` 重叠，而后者的判别标准"可观察行为变了吗？"已经覆盖了它。）

## 归档与删除

一篇 implemented 的 Agent Note，如果只描述了小的 UI 调整或者纯机械性的改动，直接删除，并修复或移除指向它的链接。一个局部的 bug 修复、性能改动、新能力或者实质性的行为决策，不会仅仅因为实现很小就够格被删。其它 implemented 笔记，只有在三个条件同时成立时才归档：上线的决策已经完成、它的理由不太可能再指导未来的工作、而这条记录仍有历史决策价值。只要它的替代方案、归属边界、否定性保证、持久化或线上协议语义、安全规则、或者重新引入的条件还有用，就保持活跃。

永远不要归档一篇 proposed 笔记——过时的提案应该被 reject。一篇 rejected 笔记只在它还能拦住一个站得住脚的错误时保留；否则删除。用 [`archive-agent-notes`](../skills/archive-agent-notes/SKILL.md) 这套校准过的工作流来判断，而不是靠字数、年龄或者一个归档配额。

归档路径编码为 `archived/{class}/yyyy-mm-dd-topic-title.md`；这里没有 `implemented` 这一层，因为只有 implemented 的笔记才可能进来。一次归档改动只做四件事：移动文件、保留 `Status: implemented`、在状态行正下方插入一行 `Archived: YYYY-MM-DD`、修复或删除指向它的入链。这是归档过程中唯一被允许的内容改动。已有的标题标点和空行排版不构成归档的障碍，原样保留即可。

一旦封存，每一篇归档笔记就**永久冻结**。不要编辑、重排、更新、移动或删除它，也不要把它当作当前行为的依据。文档门禁会跳过归档文件，包括它们的出链；活跃文档在有意引用历史时，仍然可以链接进一篇归档笔记。`npm run verify-archived-agent-notes` 强制执行封闭的 class 树、归档元数据、以及只增不改的冻结清单 `archived/manifest.json`。

## 什么时候该写一篇

只有当代码、测试和现有文档解释不了某个持久的决策理由时，才在同一个 PR 里新增或更新一篇 Agent Note。一项实质性未来工作的提案从 `proposed/` 开始；一个已经做出的决策直接从 `implemented/` 开始。选择匹配这个决策的 class 目录（见[分类](#分类)）。

更新那篇已经拥有该决策的 Agent Note 就满足规则；不要创建重复的。机械性或局部的编辑——包括局部的 UI 呈现和交互改动——豁免。一篇 Agent Note 永远不会被编辑成*另一个决策*：用一篇新的取代它，并让两篇互相链接，除非旧笔记后来依照下面的规则被完全合并。编辑一篇 `implemented/` 的 Agent Note 来跟上它既有决策的落地位置，是**必须**做的，不是被禁止的；见 [implemented/AGENTS.md](implemented/AGENTS.md)。

一篇被完全取代的 implemented Agent Note，可以合并进当前拥有该决策的笔记然后删除。删除之前，接手的那篇必须保留每一条独有的理由、替代方案、后果、必需的验证手段和已命名的覆盖缺口；修复每一条入链。**部分取代不够格**：这种情况下两篇都保留并互相链接，同时更新每一个仍然成立的事实。合并不能把旧文件改写成它的反面，也不能把 git 历史当作某条理由的唯一副本。

一篇新增能力的笔记，只有在满足全部条件时才能合并进后来那篇移除它的笔记：这个能力在生产代码、配置、schema、持久化或线上格式、迁移和兼容行为中都已不存在；没有任何现行文档把它呈现为可用；也没有任何测试把它当作受支持的行为来验证。移除的理由和验证"确实不存在"的测试可以保留。接手的那篇要保留原始动机、为什么它不再值得、除完全移除外的替代方案、放弃掉的能力、重新引入的条件，以及完全不存在的验证证据。移除一种传输方式、一个默认值、一个实现或一种呈现，都只是部分取代；任何残留的持久化数据或兼容处理也是。

## 文件格式

每篇活跃的 Agent Note 遵循同一套文件内格式，由 `npm run verify-agent-note-format` 强制（[scripts/verify-agent-note-format.ts](../../scripts/verify-agent-note-format.ts)）。归档笔记保留它被封存时的格式，外加上面那行归档日期。

### 头部块

每篇 Agent Note 的前三行严格是：

```markdown
# Agent Note: <标题>

Status: <status>
```

后面跟一个空行。`# Agent Note: ` 前缀和 `Status:` 这一行是**机械校验的标记，保持英文原样**。`Status:` 的取值是以下三种形式之一，并且必须和文件所在的 lifecycle 目录一致——门禁会交叉核对：

- `Status: proposed`
- `Status: implemented`
- `Status: rejected — <一行说明为什么>`

状态行不带日期、不带括注：文件名持有首次提出的日期，git 持有其余一切；"经修改后接受"属于正文内容（在陈述决策的地方说明修改了什么）。被否决的理由是唯一带内容的状态，因为一篇 rejected Agent Note 的结论正是读者要来找的东西。

### 正文骨架

每篇 Agent Note 的正文都以 `## 问题` 开头——写动机，并且要能脱离解决方案独立成立。后面跟什么取决于 lifecycle；反复出现的小节用下面这些规范名称，不用别的，而真正专有的技术小节（包结构、线上协议、schema）在必需小节之间自由发挥。

#### `proposed/`

```markdown
## 问题
## 方案
…专有小节…
## 曾考虑的替代方案
## 验收标准
## 风险
```

`## 方案` 是打算做的改动，**可以**用将来时——工作还没建好的时候，计划、迁移步骤和待定问题都属于这里。`## 验收标准` 说明什么样的可观察状态算做完。`## 风险` 同时覆盖可能出什么问题、以及这个改动明知故犯地放弃了什么。

#### `implemented/`

```markdown
## 问题
## 决策
…专有小节…
## 曾考虑的替代方案
## 后果
```

`## 决策` 用现在时描述已上线的现实，并且整个文件都依照 [implemented/AGENTS.md](implemented/AGENTS.md) 与之保持同步。`## 后果` 记录这个权衡**付出了什么、换来了什么**。提案期的小节标题在这里属于纸上谈兵，门禁会拒绝：`## 方案`、`## 计划`、`## 迁移计划`、`## 验收标准` 不得出现在一篇 implemented 的 Agent Note 里。`## 测试`、`## 遗留`、`## 相关` 这类小节只要陈述的是现在时的事实就没问题。

#### `rejected/`

一篇 rejected 的 Agent Note 就是被冻住的那份提案：它保留提案期原有的小节（包括 `## 验收标准` 或 `## 计划`），结论活在 `Status:` 行上。只有头部块、`## 问题` 开场、一个 `## 方案` 小节，以及下面的"曾考虑的替代方案"强制要求适用于它。

### 曾考虑的替代方案——强制

每篇 Agent Note 都带一个 `## 曾考虑的替代方案` 小节：每个真实存在过的替代方案以及它为什么落选，一个替代方案一个加粗起头的段落，或者对有争议的那个用 `### 为什么不用 <X>？` 子小节。**一个不写清楚它击败了什么的决策，等于邀请别人重新翻案**——而这正是 Agent Note 存在要防止的失败。

替代方案是被记录的，不是被编造的。如果当时确实没有考虑过任何替代方案，就如实写明这一点及其原因，不要补一个假的。

### 在 lifecycle 之间移动

把文件在 lifecycle 目录之间移动，意味着在同一个改动里更新 `Status:` 行、并重新满足目标目录的骨架要求——否则门禁会让这次移动失败。具体来说，`proposed/` → `implemented/` 要把 `## 方案` 改写成现在时的 `## 决策`，把 `## 验收标准` 和 `## 风险` 折叠进 `## 后果`（或者一个现在时的 `## 测试`/`## 验证` 小节，说明现在是什么在钉住这个行为），并且丢掉计划、只留下实际上线的东西。`proposed/` → `rejected/` 只需要在 `Status:` 行上补一个理由，然后冻结文件。
